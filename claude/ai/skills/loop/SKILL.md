---
name: loop
description: Use when asked to build a real feature end to end. Plans a spec, has an independent reviewer challenge it, implements on Opus (effort medium) with the cheap OpenCode lane doing the rote parts (more of them when a free model is on), verifies edge cases on Opus at effort high, then independent QA. Not for anything smaller than a real feature.
disable-model-invocation: true
---
Run the full loop for: $ARGUMENTS

One spec per build session. Every model call re-reads the whole conversation, so a long session costs more on every call: the 4 Oct 2026 snowlan loop built 8 specs in one session, grew from 88k to 879k tokens, and its median call re-read 672k tokens over 534 calls. You cannot run `/clear` or `/compact` yourself, so:
- When the request covers several specs (a QA batch, a list of features), do Stages 1 and 2 for all of them in this session. Then write `docs/tasks/<batch>-handoff.md`: one `## <n>. <slug>` section per spec, in build order, with its path, branch, base, planned worktree, my gate answers, and one line `Status: approved` (later `building`, `shipped` or `blocked`). Keep that line exact: `ai-night` counts the specs left by it. Stop there and ask me to start a new session with `/ai:loop docs/tasks/<batch>-handoff.md`.
- When the argument is a handoff file, read it, take the first spec that is not `shipped` or `blocked`, and start at Stage 3: its spec was already approved, so ask no Stage 1 questions and run no Stage 2. Build that one spec through Stage 5, update its section (status, commits, PR, both verdicts, open points), then stop and ask me to start the next session with the same command. When no spec is left, give the final report for the batch.
- With a single spec, run the whole loop in this session as below.

Unattended runs. When the arguments contain `unattended` (`ai-night` adds it; I am away from the computer):
- Ask me nothing and wait for nothing from me. A decision only I can make: write the question under the spec's section, set `Status: blocked`, and stop.
- Never merge, push or deploy. Leave the work on its branch, committed, and say in the handoff what is left to check.
- Run every `codex-review` call through `ai-bg`, not as a background Bash command: `ai-bg start review-<slug> -- env REVIEW_CALLER=loop codex-review diff <base>`, then `ai-bg wait review-<slug>` in the foreground until it prints the review (each wait blocks up to 9 minutes; call it again while it says `still running`). Re-reviews in Stage 5 use `codex-review recheck <base>` the same way. Run subagents in the foreground too. A headless run may end, and drop background work, when your turn ends.
- Stage 5's limit holds: when round 2 still ends at NEEDS WORK or BLOCK, write the open findings under the spec's section, set `Status: blocked`, and stop.

Conventions: specs live in `docs/specs/` as `docs/specs/SPEC-<slug>.md`; plans, task lists, handoffs and run notes for the work live in `docs/tasks/`; shipped or dropped work moves to `docs/archive/` (create the folders if missing; nothing goes at the repo root). Never overwrite an existing spec — pick a new slug. The helper commands below are on PATH while the `ai` plugin is enabled. The first output line of every helper names who actually did the work (`WORKER:` / `REVIEWER:`); carry those names into the final report.

Stage 1 — Plan (you, at the tier you're running). First ask me, in one message, the questions the request leaves open that would change the build (scope, behaviour on the edge cases you can foresee, what to leave out). Number them and put your recommended answer under each, so I can reply "ok" or change one by number. Ask only what I alone can decide: look facts up in the code yourself, or through `grunt`, instead of asking me. If my answers open new questions, ask one more round; stop when nothing the build depends on is left assumed. Skip all this when the request already answers them. Then write `docs/specs/SPEC-<slug>.md`: files to touch with exact paths, interfaces, edge cases, existing patterns to copy (name the file), and a "Done means" list where every item is verifiable (tests, build, observable behaviour). Name in it the one or two user-visible checks an e2e or integration test must prove, so that test comes from my intent and not from your reading of the code. If a folder the change touches has a nested `AGENTS.md` of gotchas, read it and name in the spec which of its lines apply. For research first ("how does the existing auth middleware work"), delegate to the `grunt` agent rather than reading everything yourself; when `grunt-run --free-status` exits 0 that research costs nothing, so prefer it for any survey longer than a few files. A spec with an open question never goes to Stage 3: list the question to me and wait (unattended: write it under the spec's section, set `Status: blocked`, and stop).

Stage 2 — Challenge the spec (independent reviewer). Run it only when the spec touches auth, payments or money, stored data or a migration, security, or concurrency. For UI, copy, config, docs and plumbing, skip it: say so in the gate message and the report, show me the spec, and end your turn as below. (10–17 Oct 2026: 49 spec reviews, 49 REVISE, while Codex went from 27% to 91% of its week.) Run in Bash:
  REVIEW_CALLER=loop codex-review spec docs/specs/SPEC-<slug>.md
Codex reviews it; if Codex is at its limit the script falls back on its own: free OpenCode models first (OPENCODE_FREE_MODELS — they keep working while OpenCode Go is at its limit), then the Go models. With the cheap lane off (`ai-lane`) there is no OpenCode fallback: Codex, else exit 75. When the `REVIEWER:` line says `free`, the review cost nothing — name the model in the report. When the `REVIEWER:` line says `downgraded`, the weekly-budget rule ran the review on the cheap Codex tier — name that in the report. If it exits with code 75, no external reviewer is reachable: delegate the same review to the `reviewer` agent and mark that review as same-vendor in the report.
Waiting rule for every `codex-review` call: run it as a background Bash command (a review often outlasts the 10-minute Bash ceiling) and do not poll it — every check is a full turn on the main model. Claude Code reports when a background command exits; until then do other independent work or end your turn. It stops by itself: a lane that reports a limit is dropped within seconds, a silent lane after 5 minutes (10 for Codex), the whole call after 35 minutes; its stderr carries a once-a-minute heartbeat for when I ask how it is going. If 36 minutes pass with no exit report, read its output once, and if it is still running, kill it and treat it as exit 75. The exit-75 line says when each lane is usable again ("codex back Tue 09:51"); copy that into the report. Calling `codex-review` again later in the session is fine: it re-checks a stored limit itself (one cheap probe, at most every 30 minutes) instead of trusting that date.
The reviewer rates each finding P0–P3 and answers REVISE only for a P0 or P1. Fold the P0/P1 findings into the spec, and the P2/P3 ones that cost a line; list the ones you rejected, with the reason. When I turn down an approach at a gate, or you drop a finding because this codebase deliberately does otherwise, propose one line for a `## Patterns we do not use` section of the root `AGENTS.md` (create it if missing, outside the managed ai-loop block): the tempting choice, what to do instead, and why. Add it only on my yes. Show me the revised spec and the verdict, then end your turn: Stage 3 starts in the turn after my yes, never in the same turn (two runs in September built before the yes, and one spec was committed before it).

Stage 3 — Build. First clear old worktrees: for each worktree under `.claude/worktrees` whose branch is merged into its base (`git branch --merged <base>`), run `git worktree remove <path>` (it refuses a tree with uncommitted changes: leave that one and name it in the report), then `git worktree prune`. Never use `--force`. Then pick the worktree: create it with `git worktree add .claude/worktrees/<slug> -b <branch> <base>` (for a stacked branch, the base is the branch below it), or reuse the one the work already lives in. Mark the branch as a loop branch with `git config branch.<branch>.ai-loop on`: the commit hook then skips its per-commit review there, because Stage 4 reviews the whole diff. Delegate to the `implementer` agent; its brief is the spec path and the worktree's absolute path. Builds go to the `implementer` only. If it cannot start, stop and tell me why. Never hand a build to `general-purpose` or another agent instead: those inherit the session's effort (max on 4 Oct 2026, hours per spec), while the implementer is pinned to medium. Pass the same worktree path to the `verifier` in Stage 3b. It writes the substantive logic itself and sends mechanical, precisely specified chunks to the cheap lane through `grunt-run`, and grunt-run moves those chunks to a headless Sonnet session when the lane is off (`ai-lane`) or every OpenCode model is limited. The implementer does a chunk itself only when no lane answers. You do not need to split that work for it.

Stage 3b — Verify (the `verifier` agent, Opus at effort high). Run it when the change has hidden edge cases: it parses, sanitises or validates input; moves money or state; handles concurrency, retries or time; touches auth, data or a migration; or fixes a bug in existing code. Skip it for UI layout, copy, config and plumbing, and say that you skipped it in the report. Brief: the spec path, the worktree path you gave the implementer, the base branch. It runs the feature, reproduces a fixed bug, and adds edge-case tests without touching production code. On `VERIFY: FAIL`, send its failing tests to the `implementer` as the brief (one round), then go on to Stage 4 with the verifier's tests included in the diff.

Stage 4 — QA (independent reviewer). Run in Bash:
  REVIEW_CALLER=loop codex-review diff <base-branch> [focus]
For anything touching auth, payments, schemas or data, pass a focus: `REVIEW_CALLER=loop codex-review diff main "auth flows, payment state, data loss"`. A focus also selects the stronger Codex tier (Sol, about 7 times Luna's cost per review), so pass one only when the diff touches auth, money, stored data or a migration. Never for content, copy, translations or docs. A `recheck` stays on the ordinary tier even with a focus. Same fallback rule as Stage 2 (exit 75 → `reviewer` agent, flagged). Every finding carries a level: P0 → BLOCK, a P1 → NEEDS WORK, only P2/P3 → SHIP with notes. The review saves a stamp of the tree it saw, for Stage 5 and `/ai:ship`. Show me the verdict.

Stage 5 — Fix loop, at most two rounds whatever the verdict. A SHIP ends the loop: its P2/P3 notes go in the report, with no fix round for them. On NEEDS WORK or BLOCK, send the P0/P1 findings to the `implementer` as its brief, plus the P2s that are a one-line fix. Then re-review with:
  REVIEW_CALLER=loop codex-review recheck <base-branch> [same focus]
It reviews only what changed since the last review, says FIXED or NOT FIXED for each earlier finding, and reports new findings only at P0 or P1 (a full review when no earlier one is usable). Never start a third round: after round 2, put the open findings first in the report, as a decision for me. (10–17 Oct 2026: 11 of 53 builds took 4–6 rounds, each a fresh full review that found a new P2.)

Gotchas: if QA found a mistake that will recur in that folder (not a one-off bug), propose one line for the nearest nested `AGENTS.md`, as a fact with the check that catches it. Show it to me; add it only on my yes. Claude Code reads a nested `AGENTS.md` on its own when it opens a file in that folder (since 2.1.277), so the folder needs no `CLAUDE.md` shim; the one-line `CLAUDE.md` files already there can stay.

Never merge. Report, in this order: what needs a decision or action from me; files changed; both verdicts with the name of the reviewer that produced each; the verify result (or why it was skipped); what was checked by running it versus only read, and what could not be checked; which chunks went to the cheap lane and on which model; the open P2/P3 notes (they stay in `docs/tasks/review-notes/<branch>.md`; commit that file with the branch);  the `ADVISOR:` lines of the implementer and the verifier; then one merge risk — the concrete thing that could still go wrong if this merged, and the check that would settle it.
